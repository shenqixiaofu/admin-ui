# 老后台改造

新后台可以从零按规矩建；老后台不行，它带着几年的历史决策。改造的本质是**在不停机的前提下换掉承重墙**。

## 一、先分级：这次改动到底是哪一种

用户说「优化一下后台」，可能指四件完全不同的事，动手前必须分清：

| 类型 | 用户实际诉求 | 该做什么 | 不该做什么 |
|---|---|---|---|
| **修 bug** | 某处点不动 / 数据不对 | 定位修掉 | 顺手重排这一页 |
| **补能力** | 缺一个筛选 / 缺一个导出 | 加功能，沿用现有视觉与结构 | 借机重构这一页 |
| **优化体验** | 「不好用，但说不上哪不好」 | 补状态、调流程、加反馈 | 重新设计视觉 |
| **重塑** | 「太丑了 / 换个风格」 | 先定方向（交给 ui-discipline 或 oil-ui），再整页重做 | 边定规范边改页面 |

**四种混在一起做，一定会翻车**。最典型的是「用户说要加快导出，结果你重排了整个页面」，交付时他找不到原来的按钮。

**判断方法**：问一句「如果只改一件事，你希望是哪件？」用户答得出的，就是真需求。

## 二、改造顺序：状态 → 结构 → 视觉

这个顺序不能反。

1. **补状态**：先让每个列表在加载、空、出错、无权限时不至于白屏。这一步**不影响视觉**，风险最低，收益最高。
2. **调结构**：信息层级、字段顺序、操作位置、筛选条件。这一步会改动 DOM，需要回归测试。
3. **改视觉**：套 token、收口裸值、统一间距。这一步改不好可以回退，但前两步改不好用户会丢数据。

**为什么不能先改视觉**：把一个仍然没有空态、没有防重复提交的表格重新配色，用户的感觉是「变好看了但还是难用」。而且下一次改动会把这次的颜色又改一遍。

## 三、盘点（先看，别动）

改造前跑一遍自检，再补三份清单：

### 1. 重复实现清单

老后台最常见的病灶不是丑，是**同一个东西有两套做法**：

```
- 三个不同版本的「日期选择器」
- 两个「确认删除」弹窗，一个用 Modal 一个用 confirm()
- 四五种 loading 写法（有的转圈、有的遮罩、有的什么都不做）
```

**先合并重复实现，再谈优化**。不合并的话，每次改规则都要改 N 处，而且一定漏。

### 2. 页面访问频率

从日志里看（没有日志就问运维）：

- **每天用**：值得改，改一次收益乘 250 个工作日
- **每周用**：值得改，但不着急
- **一年几次**：别改。把它从导航里藏起来更实际

**看着最丑的页面往往是最低频的**。按「丑」排序去改，是新手最容易犯的浪费。

### 3. 依赖清单

这一页改动了，会让哪些东西失效？

- 有没有别的地方链接到这一页（带 query 参数的深链接）
- 有没有自动化脚本 / 爬虫依赖这个 DOM
- 有没有外部系统对接这个页面的导出格式

老后台里最容易被忽略的是**深链接**：你把 `?status=1` 改成 `?status=archived`，某个同事收藏的地址就失效了。

## 四、改一页的完整流程

1. **截图存基线**（桌面 + 窄屏各一张），改完要能对比。
2. **跑自检存数字**（四态覆盖、hover-only 操作数、URL 同步数）。
3. **先补状态**，跑一次，确认没坏。
4. **再调结构**，跑一次。
5. **最后套视觉 token**，跑一次。
6. **让用户在有真实数据的库里点一遍**。空库和满库是两种体验，空库测不出分页、测不出列宽抖动。
7. **对比基线与新数字**，写进提交信息。

**每一步都要能单独回退**。一次提交里同时改状态、结构、视觉，出问题时无法定位是哪个改动导致的。

## 五、老后台的三个特有陷阱

### 1. 不要动正在被使用的接口约定

前端改动经常顺手改字段名、改请求参数。老后台的后端可能是几年前的代码，改字段名的代价远超预期。

**只改前端能改的**：渲染、布局、交互、校验。字段不改。

### 2. 保留旧路径，加新路径

深链接、书签、文档里的地址都要能打开。做法是 **旧参数兼容映射**：

```js
// 旧 ?status=1 → 新 ?status=active
const legacyMap = { '1': 'active', '2': 'archived' }
```

不要直接 404 掉。用户的收藏夹是他自己的工作记忆，你无权清空。

### 3. 不要一次性统一所有页面的骨架

「顺手把这几个页面都套上新的侧栏」听起来高效，实际上会让用户在同一天里经历 N 次陌生感。

**按模块分批**，一批一次上线，中间留一周让用户适应。

## 六、什么时候该重写而不是改

判断标准不是「有多丑」，而是：

- **数据模型错了**：页面结构跟业务模型对不上，每次加功能都要打补丁。
- **技术栈死了**：依赖的库已经停止维护，安全漏洞无法修。
- **改动成本超过重写**：一个需求要在 5 个地方各改一遍。

**只要数据模型是对的，就不该重写**。老后台的丑是表象，重写通常会把三年的业务细节丢掉，然后花两年补回来 —— 而且补的过程中，业务规则已经变了。

## 七、交付时说什么

改造完成后，交付说明里写清三件事：

1. **改了哪些状态**（之前白屏的场景现在有提示了）
2. **动了哪些约定**（深链接、导出格式、快捷键）
3. **没改的部分和原因**（哪些页面按频率判断不值得改）

第 3 条最容易被省略，但它是用户信任的来源 —— 说明你是按判断做的取舍，不是漏了。
